# 0.2 Pagefind 真实语料站内搜索召回实测

## 1. 结论摘要

1. **默认查询下 Pagefind 不能承担正文检索。** 8 条基准查询里 4 条 100%（唔、teng、LESSON、聖藥），4 条严重不足：中國 1/48（召回 2.1%）、白話報 1/21（4.8%）、廣東 8/40（20.0%，且这 8 条全部是标题字段命中，正文零命中）、唔係命中 343 篇但其中 178 篇是假阳性（精确率 48.1%）。按查询类型看：多字 CJK 词查询不可用，单字与拉丁词查询可用。
2. **根因是索引端与查询端分词不一致，docs/02 第 6.1 节的预判被证实。** 索引端（Pagefind 扩展版二进制）按词典切词：繁体专用词与粤语口语词（中國、白話、廣東、唔係、廣州）不在其词典内，被拆成单字；词典内存在的词（想起、男女、做人、何苦、平日、女子、早晨、五十）合并为单词。查询端（浏览器 JS，Intl.Segmenter，zh-Hant）把「中國」当作一个词。两端不一致时，实测退化为按首字匹配，证据是结果集完全相等：「廣州」与「廣」同为 59 篇，「風水」与「風」同为 65 篇（而「風水」正文真值只有 1 篇）。
3. **单字、罗马字、英文查询完好。** 唔 426/426、teng 21/21、LESSON 135/135，召回与精确均 100%。这是 Pagefind 在本语料上唯一可靠的三类查询。
4. **口语词默认查询是超集而非精确匹配。** 「唔係」被查询端切成 唔 与 係 两字并按 AND 匹配，命中 343 篇（等于两字全篇共现数 343），召回 100%、精确 48.1%；加引号的精确查询可还原相邻短语（165/165，与真值一致）。
5. **站点侧查询改写（汉字逐字拆开并加引号）能把召回补到 100% 左右**，但在原始索引上仍漏 1 篇（gdvp-01-012-01，该篇「中國」的「中」被索引端并入「口中」），且对索引端已合并成词的文本反向漏召（想起、男女、女子、早晨 等 10 余词全部落空）。该做法依赖未公开行为，不建议产品化，仅作为下策备选记录。
6. **不需要为 Pagefind 做前处理。** 把全部汉字之间插入零宽空格（ZWS）重建索引后，默认查询结果与未处理版逐条相同（第 4.5 节），前处理救不了默认查询路径。
7. **降级为「只搜标题」不可取。** 866 篇中只有 297 篇有标题（34.3%），标题索引只覆盖三分之一语料，且多字 CJK 词在标题索引里同样退化（廣東 8/10、白話報 1/6）。
8. **最终判断：Pagefind 只宜作辅助，主检索仍走 D1 FTS5 trigram。** 0.1 已实测 trigram 对 3 字及以上查询 100% 召回、100% 精确（中位延迟 0.03 至 0.13 毫秒），1 至 2 字走 bigram/unigram 辅助表同样 100%。若确实需要 Pagefind，其合理用途是标题与罗马字的前端即时提示（autocomplete），且必须明示不覆盖正文。

## 3. 方法

### 3.1 生成页与索引

`scripts/gen-site.mjs` 逐行读三个 articles.jsonl，按篇输出 `site/a/<id>.html`，同时对标题与正文做 HTML 实体转义。文件名即文章 id，用于把检索结果映射回真值。建索引命令为 `npx pagefind --site site`（默认输出到 `site/pagefind/`）。

### 3.2 真值口径

`scripts/gt.py` 用 Python 直接在发布层上做子串统计：中文严格子串，拉丁按 ASCII 大小写不敏感（与 Pagefind 的拉丁折叠一致）。统计范围为标题与正文的并集（因为生成的 HTML 两者都参与建索引），同时记录仅正文的口径，便于与 0.1 的 trigram 结果对照。

查询真值表：

| 查询 | 仅正文真值（0.1 口径） | 正文并标题真值 | 备注 |
|---|---:|---:|---|
| 廣東 | 34 | 40 | 6 篇仅标题含 |
| 唔係 | 165 | 165 | 完全在正文 |
| 白話報 | 16 | 21 | 5 篇仅标题含 |
| 中國 | 48 | 48 | 完全在正文 |
| 唔 | 426 | 426 | 完全在正文 |
| teng | 21 | 21 | 传教士罗马字 |
| LESSON | 28 | 135 | 107 篇仅标题含（书目章节标题） |
| 聖藥 | 2 | 2 | 完全在正文 |

### 3.3 查询执行

Pagefind 的 Node API 只提供建索引，没有检索接口。实测做法：起本地 HTTP 静态服务，在 Node 里 `import` 生成包的 `pagefind/pagefind.js`（ES 模块），用 `createInstance({ basePath })` 指向该服务，并给全局补一个最小的 `document` 垫片模拟浏览器 `<html lang="zh-Hant">`（决定查询端语言与分词路径）。检索结果按 `data-pagefind-meta` 里的 `article_id` 映射回文章 id。

为确认两端实际收到的查询串，另做了一次插桩：复制一份 pagefind.js 并在 wasm 绑定的 `search()` 入口打印 `query` 参数，日志显示查询端交给 wasm 的确实是分词后空格连接的串（如「中國」「唔 係」「中國 人」「聖 藥」）。

### 4.3 分词不一致的实测证据

三个层次各有一组可直接复现的证据。

**索引端切词不按繁体词典。** 检索结果里取回正文片段，其内部以零宽空格分隔索引词。样本：`"唔\u200b想\u200b就\u200b罷\u200b.\u200b[\u200b解\u200b心\u200b]\u200b唔\u200b想\u200b就\u200b罷\u200b。\u200b想起\u200b越\u200b發\u200b傷\u200b神\u200b。\u200b做人\u200b何苦\u200b。\u200b亂\u200b種\u200b情\u200b根\u200b。\u200b平日\u200b自己..."`。可见 唔、想、就、罷 是独立单字，而 想起、做人、何苦、平日 被合并为单词。繁体／粤语专有词（中國、白話、廣東、唔係、廣州、聖藥）在这些样本里从未作为单词出现。

**查询端切词按现代词典。** Node 的 `Intl.Segmenter("zh-Hant", "word")` 实测：中國、白話、廣東、廣州 各是一个词；白話報 切成 白話 与 報；中國人 切成 中國 与 人；唔係、聖藥、邊個 切成两个单字；東白、話報 切成两个单字。与索引端的切法系统性错位。

**错位后的退化行为是「按首字匹配」。** 三组对照，结果集逐条相等：

| 查询对 | 命中篇数 | 结果集是否相同 | 真值（正文） |
|---|---:|---|---:|
| 廣州 与 廣 | 59 与 59 | 相同 | 廣州 7 篇（假阳性 52 篇） |
| 風水 与 風 | 65 与 65 | 相同 | 風水 1 篇（假阳性 64 篇） |
| 邊個（切成 邊、個）与 邊 | 109 与 129 | 不相同（AND 语义） | 邊個 19 篇 |

「唔係」343 篇等于 唔、係 两字的全篇共现数 343，进一步说明默认多词查询是 AND 而非相邻短语。加引号后转为精确短语语义：「唔 係」165/165、「廣 東」40/40、「白 話 報」21/21、「聖 藥」2/2，召回与精确均 100%。

**反向漏召同样存在。** 索引端已合并成词的字，拆字短语查询会落空：想起（正文真值 13）默认查询 13/13，拆字精确查询 0/13；男女 10/10 对 0；女子 17/17 对 0；早晨 9/9 对 0；做人 3/3 对 0。也就是说，同一批语料里，一部分词只能整词查，另一部分词只能拆字查，而站点无法预先知道哪些词属于哪一类（切词器不公开、无接口）。

### 4.4 单字与拉丁查询

单字：唔 426/426、中國的 中 175/198（差额 23 篇是「中」在这些篇里不以单词形式出现，已核实的一例是 gdvp-01-012-01 的「中」被并入索引词「口中」）、白 111/151、其他常用单字命中与真值一致。
拉丁：teng 21/21、LESSON 135/135，精确 100%；子串与前缀行为正常（t 555 篇、te 264 篇、tra 54 篇、trans 38 篇，符合 Pagefind 文档中的末尾词前缀匹配语义）。英文大小写不敏感（LESSON 与 lesson 同为 135 篇）。全文索引对拉丁查询无问题。

### 4.5 变体实验

**变体一：查询改写（不改索引）。** 站点侧把汉字查询逐字拆开，两种用法：

| 查询 | 拆字（AND 语义） | 拆字加引号（短语语义） |
|---|---|---|
| 廣東 | 42 篇，召回 100%，精确 95.2% | 40 篇，100%/100% |
| 唔係 | 343 篇，召回 100%，精确 48.1% | 165 篇，100%/100% |
| 白話報 | 30 篇，召回 100%，精确 70.0% | 21 篇，100%/100% |
| 中國 | 79 篇，召回 97.9%，精确 59.5% | 47 篇，97.9%/100% |
| 聖藥 | 2 篇，100%/100% | 2 篇，100%/100% |
| 唔 | 426 篇，100%/100% | 426 篇，100%/100% |

「拆字加引号」在原始索引上达到 100% 召回与 100% 精确（中國漏 1 篇，gdvp-01-012-01，原因见第 4.3 节末）。代价与风险：依赖 `Intl.Segmenter` 与 exact 短语的未公开组合行为；对索引端已合并的词反向漏召；查询延迟略增（同量级，均低于 5 毫秒）。

**变体二：前处理（汉字间插零宽空格）重建索引。** 866 页全量重建，产物 4.7 MB，与未处理版相同。默认查询（廣東、唔係、白話報、中國、唔、聖藥）的结果与未处理版逐条相同，无任何改善；拆字加引号方案则把中國补到 48/48（ZWS 强制全部汉字单字化，消除了「口中」这类合并）。结论：前处理对默认查询路径无效，只为拆字方案补漏，收益不足以支撑构建期改造与语料侵入。

**变体三：只搜标题。** 只把 h1 放入 `data-pagefind-body` 重建：866 篇中仅 297 篇有可索引内容（34.3%），去重词 581 个，产物 1.7 MB。查询表现：LESSON 113/113（标题真值 113）、唔 2/2、唔係 1/1、聖藥 1/1、廣東 8/10、白話報 1/6、中國 1/2，拆字加引号后可到廣東 10/10、白話報 6/6、中國 2/2。标题索引里同样存在退化：查询 teng 命中 1 篇标题为「T.」的文章（词典退化兜底，机制未完全定位，标为待验证）。

## 6. 判断、建议与未验证项

**判断：**

1. Pagefind 默认查询不能承担本站的正文检索，主检索仍走 D1 FTS5 trigram（0.1 的结论不变）。
2. 是否需要前处理：不需要。ZWS 前处理对默认查询无改善，只会增加构建复杂度与语料侵入。
3. 是否需要降级为只搜标题：不需要也不充分。若采用 Pagefind，应按用途限定为标题与罗马字的即时提示，并在界面上明示「不含正文」。
4. 查询改写（拆字加引号）可作为研究记录保留，不建议产品化：它依赖未公开行为，且对索引端已合并的词会漏召，维护风险高于收益。若未来必须用 Pagefind 做正文检索，应先向上游确认切词器与查询管线是否可配置，或改用可控的自建索引。

**未验证项（进入 Phase 1 前如需上线 Pagefind 再做）：**

1. 浏览器端实测：本次在 Node 中运行生成包，Safari、Firefox、移动端对 `Intl.Segmenter` 的词典与实现差异可能改变查询端切词结果，需在真实浏览器中复测第 4.2 节基准。
2. Cloudflare 线上形态：静态文件数（第 4.1 节约 892 个新增文件）、片段与分片的缓存行为、首次搜索的载荷（wasm 68 KB 加元数据与首个分片）未在真实站点测量。
3. Pagefind 版本与配置变化：本次只用 1.5.2 默认设置；`--force-language`、`--include-characters` 等选项未做对比实验。
4. 索引端切词的确定规则：本次由行为反推（词典内词合并、词典外按字），未阅读 Pagefind 源码确认，标为待验证。

| `scripts/gen-site.mjs` | 从发布层生成 866 个测试页（`site/`） |
| `scripts/gt.py` | 真值统计，输出 `gt.json` |
| `scripts/measure.mjs` | 基准查询与召回/精确率统计，输出 `measure-<tag>.json` |
| `scripts/zws-build.mjs` | 零宽空格前处理变体（`site-zws/`） |
| `scripts/title-build.mjs` | 只搜标题变体（`site-title/`） |
| `scripts/probe.mjs`、`scripts/battery.mjs`、`scripts/merged.mjs` | 分词行为探针 |
| `patch/pagefind.js` | 插桩副本，用于打印 wasm 实际收到的查询串 |
| `gt.json`、`measure-orig.json`、`measure-zws.json`、`battery.json` | 原始结果 |

复现步骤：`npm i pagefind`（本机为 1.5.2）；`node scripts/gen-site.mjs`；`npx pagefind --site site`；`python3 scripts/gt.py`；`node scripts/measure.mjs site orig`。
